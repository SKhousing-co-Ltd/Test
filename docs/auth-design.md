# 基幹システム向け認証・権限設計

## 1. 認証方式

本システムの認証方式には **Supabase Auth の Google OAuth** を採用する。ログインは会社の Google Workspace アカウント（`@sk-housing.jp`）で行い、メールアドレス・パスワードによるアプリへのログインは提供しない。

Google OAuth アプリは Google Workspace 内部向けに設定し、`hd=sk-housing.jp` はアカウント選択のヒントとして利用する。`hd` パラメーターだけをドメイン制限の根拠にはしない。Supabase の発行するセッションと JWT を使ってアプリ内のユーザー識別・認可を行う。

一般利用者のセルフサインアップは無効のままとし、管理者がアカウント管理画面で会社メールアドレス、担当者、ロールを登録する。登録時点で利用可能とし、初期パスワードの発行・変更は不要とする。

Google OAuth の有効化、Google Cloud OAuth クライアント、Supabase の認証コールバックURL、およびアプリの許可リダイレクトURLは環境ごとに設定する。

## 2. 想定ロール

本システムでは、以下のロールを想定する。

| ロール | 概要 |
| --- | --- |
| `admin` | システム全体の管理者。ユーザー管理、権限管理、全機能の操作を行える。 |
| `manager` | 業務管理者。担当範囲の業務データ確認、承認、マスタ情報の一部管理を行える。 |
| `staff` | 一般担当者。日常業務に必要なデータ登録・更新・参照を行える。 |
| `viewer` | 参照専用ユーザー。許可された情報の閲覧のみ行える。 |

## 3. ロールごとのアクセス可能機能

| 機能 | `admin` | `manager` | `staff` | `viewer` |
| --- | --- | --- | --- | --- |
| ダッシュボード閲覧 | 可 | 可 | 可 | 可 |
| 業務データ閲覧 | 可 | 可 | 可 | 可 |
| 業務データ登録 | 可 | 可 | 可 | 不可 |
| 業務データ更新 | 可 | 可 | 可 | 不可 |
| 業務データ削除 | 可 | 不可 | 不可 | 不可 |
| 承認・差戻し | 可 | 可 | 不可 | 不可 |
| マスタデータ閲覧 | 可 | 可 | 可 | 可 |
| マスタデータ登録・更新 | 可 | 一部可 | 不可 | 不可 |
| ユーザー管理 | 可 | 不可 | 不可 | 不可 |
| ロール・権限管理 | 可 | 不可 | 不可 | 不可 |
| 監査ログ閲覧 | 可 | 可 | 不可 | 不可 |
| システム設定 | 可 | 不可 | 不可 | 不可 |

※ 「一部可」は、業務要件に応じて管理対象のマスタを限定する。

## 4. フロント側の保護ルート方針

フロントエンドでは、認証状態とロール情報に基づいて保護ルートを制御する。

- 未ログインユーザーが保護対象ページへアクセスした場合は、ログインページへリダイレクトする。
- ログイン済みユーザーであっても、必要なロールを持たないページへアクセスした場合は、権限不足ページまたはダッシュボードへ遷移させる。
- 画面表示だけでなく、ナビゲーションメニューや操作ボタンもロールに応じて出し分ける。
- フロント側の制御はユーザー体験向上のための補助的な制御とし、最終的なアクセス制御は Supabase 側のポリシーで担保する。
- セッション失効時は Supabase Auth のセッション状態を検知し、ログインページへ誘導する。

## 5. Supabase 側の Row Level Security 方針

Supabase 側では、業務データを保持する各テーブルで **Row Level Security（RLS）を有効化する** 前提とする。

RLS ポリシーでは、Supabase Auth のユーザー ID とロール情報を利用し、テーブル単位および行単位でアクセス可否を制御する。フロントエンドからのリクエストは改ざん可能であるため、データベース側で必ず以下を担保する。

- ロールごとに許可された操作（SELECT / INSERT / UPDATE / DELETE）のみ実行できること。
- ユーザーがアクセス可能な組織・部門・担当範囲のデータのみ参照・更新できること。
- `viewer` は参照系操作のみ許可し、更新系操作を許可しないこと。
- `admin` であっても監査要件に応じて操作ログを記録できること。

これにより、フロント側の保護ルートと Supabase 側の RLS を組み合わせ、多層的な認証・認可を実現する。

## 6. アカウントと担当者の紐づけ

- `auth.users` と `employee_master` は `user_profiles` を介して最大1対1で紐づける。
- 管理者はアカウント管理画面で `@sk-housing.jp` のメールアドレス、在籍中の担当者、ロールを登録する。Authユーザーとプロフィールを作成し、`account_status = 'active'`、`must_change_password = false` として直ちに利用可能にする。
- Authユーザー作成時の既存トリガーはプロフィールを初期化する。その後、管理者用 Edge Function が選択された担当者・ロール・有効状態を設定する。
- 利用者は登録されたメールアドレスと同じ Google Workspace アカウントでログインする。既存 Auth ユーザーへの Google identity 紐付け後も `auth.users.id` を維持し、業務データの作成者・承認者などの参照を変えない。
- 既存アカウントの移行では、既存のメールアドレスと社員紐付け・ロールを維持する。移行前に Google identity が正しい既存ユーザーへ紐付くことを確認する。
- `employee_master.employment_status` が `inactive` になった場合、紐づくアカウントは `suspended` に同期する。過去の業務履歴は削除しない。
- 初回の管理者は、対象アカウント作成後に Supabase SQL Editor で `user_profiles.role` を `admin` に更新して設定する。
